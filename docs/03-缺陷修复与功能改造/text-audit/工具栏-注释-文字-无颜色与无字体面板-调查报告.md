# 工具栏「注释 → 文字」：无颜色显示 + 无字体控制面板 · 调查报告

> 调查方式：Agent Teams（6 个角度并行取证 → 4 条根因假设独立对抗验证 → 综合判决），
> 全部结论逐条回读源码复核。快照：工作区 `HEAD=1ef785d`（分支 `dev_hy`，含未提交改动）。
> 相关既有审计：`docs/03-缺陷修复与功能改造/text-audit/汇总表-按严重级别.md`（快照 `534da15`）。

## 0. 结论速览

用户报告的两个症状**不同源**：

| 症状 | 根因 | 置信度 | 状态 |
| --- | --- | --- | --- |
| 文字没有字体控制面板修改 | Write 模式下内置 MTEXT 工具栏被挂进 `display:none` 容器；替代品「MTEXT 上下文功能区」已在删除旧壳时整体删除且未移植 | **高（可无条件复现）** | 既有审计 **P2-7**，被标为「低优先 未修复」 |
| 绘制输入文字时占了位但没有颜色显示 | **未定论**，有 3 个可区分的候选机制（见 §2） | 中 | 其一为本次新发现（未提交改动引入的竞态） |

对抗验证阶段 4 条假设的裁决结果全部是 `partially-confirmed`：**没有任何一条被无条件证实**，
所以症状一必须以运行时观测（浏览器 console）区分，不能只靠读码下结论。§3 给出判别步骤。

## 1. 症状二：没有字体控制面板（已定论）

### 1.1 结论

内置 `MTextInputBox` 工具栏是**唯一**的字体/字高/颜色控件（字体族下拉、字号输入框、颜色选择器），
它被完整地创建出来，却被挂进一个 `display: none` 的隐藏容器；而设计上用来替代它的
「MTEXT 上下文功能区」在 `809e4fe`「删除旧 Element Plus 壳」时被整体删除、从未在 Antd 壳重建。
因此**全应用不存在任何字体控制面板**。

### 1.2 证据链（逐行复核）

1. **默认就是写模式**：`packages/cad-viewer-example/src/App.vue:188`
   `const selectedMode = ref<AcEdOpenMode>(AcEdOpenMode.Write)`
2. **写模式 ⇒ 关掉内置工具栏**：`packages/cad-viewer-example/src/shell/useAntdCadShell.ts:315-322`
   ```ts
   watch(() => options.mode.value,
     mode => { AcEdMTextEditor.setDefaultToolbarEnabled(mode !== AcEdOpenMode.Write) },
     { immediate: true })   // 挂载即执行
   ```
3. **而 MTEXT 编辑器只可能在写模式打开**：`AcApMTextCmd.ts:65-68`（`this.mode = AcEdOpenMode.Write`）、
   双击路径 `AcTrView2d.ts:685-687` 同样要求 Write。故「工具栏可见」的分支（`mode !== Write`）**不可达**。
4. **隐藏容器的实现**：`AcEdMTextEditor.ts:635`（`toolbarEnabled = AcEdMTextEditor.defaultToolbarEnabled`）
   → `:708-710`（`toolbarEnabled ? null : createHiddenToolbarContainer(view.container)`）
   → `:462-473`：`display:'none'; pointerEvents:'none'; aria-hidden`。
5. **但工具栏仍被无条件创建**：`AcEdMTextEditor.ts:754-758` 硬编码 `toolbar: { enabled: true, container: hiddenToolbarContainer ?? view.container, ... }`。
   第三方 `mtext-input-box/dist/viewer/viewer.js:262,1136-1142` 因此照常 `mountToolbar` + `setVisible(true)`。
   `position: fixed` 也逃不出 `display:none` 祖先，于是 DOM 存在、样式正常、就是不可见不可点。
6. **工具栏本身是完整的**（被证伪的替代解释：「字体列表为空才没有下拉」不成立）：
   `dist/ui/toolbar.js:5-16` 定义 12 个内置通用字体族；`:200-211` `resolveFontFamilies` 在传入列表为空时回退到它们；
   `:234-243` 无条件 append option → 字体下拉始终渲染。字号输入、颜色选择器同在 `:244-261`。
7. **替代品不存在**：
   - 类型与样式是**死代码**：`ribbonTypes.ts:72-85` 的 `RibbonContextualConfig`、`AntdRibbon.vue:29-33` 的
     `is-contextual`、`shell.css` 的 `.is-contextual::before`；`ribbonModel.ts:337-368` 的 6 个 tab **无一设置 `contextual`**。
   - 格式桥**无任何调用者**：`AcEdMTextEditor.ts:368` 的 `addActiveInputBoxChangeListener` 全仓 grep 零命中
     （`getActiveInputBox()` 的调用者全是按键/夹点/选择守卫，没有一个是格式 UI）。
   - 被删掉的正是完整实现：`git show --stat 809e4fe` 显示删除
     `useMTextContextualRibbon.ts`（**1725 行**）、`MlRibbonFontSelect.vue`、`MlRibbonMTextHeightSelect.vue`、
     `useRibbonContextualTab.ts`；当前仓内 `find` 无任何对应文件。
8. **颜色选择器的接线是好的**，只是跟着工具栏一起被隐藏：
   `packages/cad-viewer/src/app/app.ts:33` `registerMTextColorPicker()` → `register.ts:157-164`
   → `AcEdMTextEditor.ts:760-763` `colorPicker: toolbarColorPicker ?? AcEdMTextEditor.defaultColorPicker`。

### 1.3 与既有审计的关系

这正是既有审计 **P2-7「富文本级格式控件无入口，内置工具栏被挂进 `display:none` 容器」**
（`A3-2`，partially-confirmed，文件/行号 `useAntdCadShell.ts:315-322`）。
本次独立复查与该条目逐字吻合，**没有新机制**——但该条目被标为「⬜ 未修复（低优先）」，
而实际上它导致用户在**唯一可编辑的模式**下完全没有字体面板。建议重新定级。

### 1.4 修复建议

- **首选（最小改动，1 行）**：`useAntdCadShell.ts:319` 写模式保留内置工具栏，即
  `AcEdMTextEditor.setDefaultToolbarEnabled(true)`；或改为只有宿主确实提供上下文功能区时才关闭。
- **不要**顺手把 `AcEdMTextEditor.ts:754` 的 `enabled: true` 改成 `toolbarEnabled`：该处硬编码是**有意**的，
  注释（`:704-707`）说明输入框需要这个共享工具栏对象做内部格式同步，`enabled:false` 可能连带破坏格式同步。
- **不要**走「移植被删的 1725 行上下文功能区」这条路，除非产品上确实要功能区形态。
- 另建议：`setDefaultToolbarEnabled(false)` 时在 `AcEdMTextEditor.open()` 里补一条
  「无替代 UI」的开发期告警，避免同类静默回归。

## 2. 症状一：占了位但没有颜色显示（未定论，3 个候选）

三种机制都能产出「框在、位置在，但看不到字」。它们的**可观测特征互不相同**（§3）。

### 候选 A（本次新发现，优先排查）：字体目录/字体字节拿不到 ⇒ 只画占位框

- `mtext-input-box/dist/viewer/viewer.js:1247-1256`：字形绘制被单一 `rendererReady` 把关，
  它只在 `await loadFonts(['simkai'])` 不 reject 时置真；失败只 `console.error`，且该会话内不再重试。
- `viewer.js:1258-1266`：`!rendererReady` 时 `createFallbackCharBoxes()` 后直接 return。
- `viewer.js:1571-1611`：占位实现按 `width = Math.max(1, fontSize * 0.6)` 逐字符 **推进笔位**，
  `:1630-1647` 用该占位布局重算包围框 ⇒ **框随打字变大、一个字形几何都没有**——与「占了位但没有显示」逐字吻合。
- `defaultFontLoader.ts:100-104,189-198`：`load()` 第一件事 `await getAvailableFonts()`，
  即先 fetch `<base>/fonts.json`；取不到就抛，异常被吞。
- **本工作区的现实触发路径（未提交改动引入）**：`App.vue` 已把 `BASE_URL` 换成
  `cadDataBaseUrl = ref(CAD_DATA_CDN_BASE_URL)`，再由异步探针改写为本地镜像：
  ```ts
  const cadDataBaseUrl = ref(CAD_DATA_CDN_BASE_URL)
  void resolveCadDataBaseUrl({ appBaseUrl: import.meta.env.BASE_URL }).then(url => { cadDataBaseUrl.value = url })
  ```
  而 `onViewerCreate()` 里的 `fetch(\`${cadDataBaseUrl.value}fonts/hztxt.shx\`)` **不等待探针**；
  同时 `AntdCadViewer.vue:218` 的 `useAntdCadShell({ baseUrl: props.baseUrl })` 是 **setup 时一次性取值**
  （普通属性，不是 getter），探针晚于挂载完成时后续变化不会传播。
  ⇒ 探针未落地（最多 `probeTimeoutMs = 2000ms`）时，`hztxt.shx` 与 `fonts.json` 都会走 jsDelivr；
  在国内网络下 jsDelivr 常不可达 → `hztxt` 字节**没有**写进 worker 共享的 IndexedDB 缓存
  （`AcTrMTextRenderer.ts:636-666` 的 `cacheFont` 是唯一同时服务主线程与 worker 的通道），
  MTEXT 输入框就落到「零字形」分支。
  ⚠️ 这是相对改动前（`fetch('./fonts/hztxt.shx')`，同源、无 CDN 依赖、无竞态）的**回归风险**。
- 次级变体：`fonts.json` 可达但 `simkai` 在目录中不存在（本地 `fonts.json` 只有 `amgdt/hztxt/simplex/simsun`），
  `load()` 对该名字返回 `NotFound`（**不抛**，见 `defaultFontLoader.ts:130-180`），
  随后由 `FontManager` 的 `defaultFonts` 兜底——而 `App.vue:228` 调 `setDefaultFonts(['hztxt'])`
  **替换**掉了默认的 `['simsun']`（`fontManager.ts:96`）。若 `hztxt` 未加载成功，兜底链为空 ⇒ 字形为空。
  这也解释了「图纸里的字看得见、输入框里的字看不见」：图纸侧还能命中 `simsun.woff`，输入框侧的兜底链只剩 `hztxt`。

### 候选 B：浅色但非纯白的背景 ⇒ 预览字与背景同色

- `AcApDocManager.ts:895-898` 用**严格相等**判明暗：
  `const bg = this.curView.backgroundColor; return bg === 0xffffff ? 0x000000 : 0xffffff`
- 而全仓其他地方（`AcGiContext.ts:95-117` 的 BT.601、`AcEdUiColor.ts:231/261`、
  `AcEdMTextEditor.ts:646-647` 的光标）都用**亮度阈值**。
- 背景 `#F0F0F0`（luma>128 且 ≠0xFFFFFF）时：预览字 = 0xFFFFFF（白字压浅底 ⇒ 不可见），
  光标 = `#000000`（可见）、包围框恒为 `#58a6ff`（可见）——正是「框和光标在、字看不见」。
- 传导链：`AcEdMTextEditor.ts:650` 取 `layerColor` → `:748-753` 作为 `byLayerColor`，
  `color: new MTextColor()` 默认 `aci = 256`（`@mlightcad/mtext-parser/dist/parser.js:1435`）
  → `viewer.js:1773-1789` `resolveBaseFormatColor` 落到 `{aci:null, rgb: byLayerColor}`。
- **触发条件**：需要把 `MODELBKCOLOR`/`PAPERBKCOLOR` 设成非纯黑白颜色（命令行敲 `MODELBKCOLOR` 即可，
  每个 sysvar 都自动注册了同名命令）。纯黑/纯白与 switchbg 都不触发。
- 修复：把 `resolveAci7ForBackground` 改为复用 `acgiIsLightBackground(bg)`，与全仓判据统一（1 行）。

### 候选 C：内联 `\c` 绝对化 ⇒ 提交后失去 ACI-7 反色（既有审计 P2-8 / P2-22）

- 内联编辑会把「前景语义」在写入时绝对化成 run 级 `\c<十进制RGB>`、`\H`：
  `AcApMTextCmd.ts:142` 原样入库；`AcEdMTextEditor.ts:533`（配 `469-474`）为审计定位点。
- 后果：实体颜色/图层色/文字高度对这批文本失效（属性面板改字号、颜色「无变化」）。
- 「背景翻转后不可见」只在特定方向成立：默认 worker 路径有回推
  （`mtext-renderer/src/renderer/colorUtils.ts:90-109` 把与实体基准解析色相等的绝对 RGB 回推为 ACI），
  暗底烘焙的 `\c16777215;` 翻白底会被救回；亮底烘焙的 `\c0;` 与
  main 线程模式（`useMainThreadDraw=true`）两个方向都救不回，
  且 `AcTrMTextColorUtil.ts:211-219` 会把「与 expectedFg 不同的绝对 RGB」当作真正的内联覆盖而拒绝重材化。
- 状态：审计标 **❌ 未修复（阻塞项）**，且是「改字号/颜色无变化」的同源缺陷。

### 已被证伪的解释（不要再查这两条）

- **透明/遮挡**：字形材质是 `new THREE.MeshBasicMaterial({ color })`（`defaultStyleManager.ts:19-39`），
  opacity 默认 1，全仓无处给字形设 opacity；`viewer.js:1687-1708` 只做 `transparent = opacity < 1`。
- **`mtextProcessor.ts` 强制 `depthTest=false`**：第一阶段的一条引证有误——
  `packages/mtext-renderer/src` 全仓 grep `depthTest|depthWrite` 零命中，
  `depthTest=false` 的唯一来源是输入框自己的 `viewer.js:1699-1702`，且它是**增强**可见性。

### 需要澄清的既有条目状态

审计表中 **P1-8「离线时 worker 无任何字体，汉字退化为空白占位」标 ❌ 未修复（阻塞项）**，
但快照之后的最新提交 `cc3164d` 已改 `App.vue` + `AcTrMTextRenderer.ts`（+601/−23）：
`App.vue:200-225` 现在走 `AcTrMTextRenderer.getInstance().cacheFont(...)`，
把字体二进制同时写进 worker 读取的 IndexedDB 缓存；`AcTrMTextRenderer.ts:636-666` 的注释明确写了这一点。
**该条目的状态相对 HEAD 已过期**，应在下次审计时重判。

## 3. 判别步骤：如何在 2 分钟内定位症状一

在浏览器里点「注释 → 文字」、框选、然后**输入中文**，同时看 DevTools Console：

| 观测 | 判定 | 处理 |
| --- | --- | --- |
| `[mtext-input-box] Failed to initialize mtext renderer fonts` | 候选 A（主变体）：`fonts.json` 取不到 | 查 Network 里 `fonts.json` / `hztxt.shx` 的 URL 与状态码；确认探针是否已落地、本地镜像是否已 `pnpm sync:cad-data` |
| `[mtext-input-box] Failed to sync render MTEXT` | 候选 A 的 ready 分支失败 | 同上，另查是否有可用兜底字体（`FontManager.defaultFonts`） |
| 无报错，框随打字变大但**一个字形都没有** | 候选 A 的字体字节变体 | 查 IndexedDB 字体缓存是否有 `hztxt`；核对 `setDefaultFonts(['hztxt'])` 是否替换掉了可用的 `simsun` 兜底 |
| 有字形但**与背景同色** | 候选 B | 把 `MODELBKCOLOR` 设为 `240,240,240` 复现；统一 `resolveAci7ForBackground` 判据 |
| 出现后才消失、或平移/缩放后才出现 | 重绘时序（审计 X-1，**已在 `cc3164d` 修复**） | 确认跑的是 `cc3164d` 之后的构建；`AcEdMTextEditor.ts:822` 的 `view.isDirty = true` 是否在运行 |
| 输入时可见，**提交后**不可见 / 切背景后不可见 | 候选 C（P2-8 / P2-22） | 按审计条目修内联 `\H`/`\c` 序列化策略 |

**重要前提确认**：先确认用户测的是哪个构建。`ck3164d` 同时修了 X-1（打字不重绘）与 P1-8（字体进 worker 缓存），
若用户跑的是更早的构建或未重建的 `dist`，症状一会整体表现为「打字完全看不到字」。

## 4. 本次调查的边界（未验证项）

- **没有做浏览器/GPU 目视复现**，也没有跑 E2E（`mtext-draw-accuracy.spec.ts` 只覆盖「命令前空白 / 提交后出墨」的因果对照，
  不覆盖工具栏可见性、字体面板、输入框内着色）。
- 因此**症状一的具体触发分支未定论**；上文 §3 是判别方案，不是结论。
- 4 条对抗验证结论均为 `partially-confirmed`：机制方向对，但触发条件都被收窄
  （例：候选 B 的第一阶段证据误称「host 有 `background` 选项」，实际 `AcApDocManagerOptions` 无该字段，
  且 `AcTrView2dOptions.background` 从未被转发、还会被 `syncDisplaySysVars` 覆盖；真实入口是 `MODELBKCOLOR/PAPERBKCOLOR`）。
- 未核实的次要项：中文 IME 组合键路径（`compositionstart/update/end`）是否也影响可见性。

## 5. 建议的落地顺序

1. **修复症状二**（1 行，风险低，用户立刻可感知）：`useAntdCadShell.ts:319` 写模式保留内置工具栏。
2. **消除候选 A 的竞态**（未提交改动内的回归）：让 `onViewerCreate` 里取字体前 `await` 同一个
   `resolveCadDataBaseUrl()` promise（该函数已有按 `<local>|<fallback>` 的 `probeCache`，重复调用是幂等的）；
   同时把 `AntdCadViewer.vue:218` 的 `baseUrl` 改为响应式（传 getter / `toRef`），
   或在 `useAntdCadShell` 内 `watch` 后调用 `setBaseUrl`。
3. **统一明暗判据**（1 行）：`AcApDocManager.ts:895-898` 复用 `acgiIsLightBackground`。
4. **补回归测试**：断言「写模式下 MTEXT 编辑器存在可见的格式控件」（可查 DOM 中工具栏宿主不在 `display:none` 子树内）；
   补一条浅灰背景（`MODELBKCOLOR=240,240,240`）下预览字对比度的用例。
5. **清理既有审计状态**：P2-7 提级；P1-8 按 `cc3164d` 重判。
