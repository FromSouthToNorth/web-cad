## 2. TL;DR

1. **字高来源错是最高优先级的准确性缺陷**：新建 MTEXT 的字高取「当前视图下 24 CSS 像素的世界当量」（`AcApMTextCmd.ts:38`），与框选尺寸和文字样式 `TEXTSIZE` 都无关，随缩放漂移并被编辑器静默夹到 1 世界单位后写进 DXF 组 40（A1-1，P1）。
2. **默认 worker 渲染模式下「缺字体」是全程静默的**：worker 只回传 `fontLoaded`，`fontNotFound` 与 `missedFonts` 在主线程恒为空（A4-2，P1）。
3. **离线时汉字可能整段变空白**：本地 `hztxt.shx` 只注册进主线程 `FontManager`，worker 拿不到字库字节，且离线会让 `getAvailableFonts()` 抛错挡住 IndexedDB 回退（A4-3，P1，已由对抗式验证在渲染器 0.12.4 上零字体复现：6 个汉字得到 0 个几何叶子、box 宽 4.5 = 占位宽度）。
4. **双击编辑会破坏既有图纸**：只打开编辑器（甚至按 Esc 取消）就把 `lineSpacingFactor` 由 DXF 约定的 1.0 改写成 0.3 并立即入库；`height` 也会被 `Math.max(1,·)` 归一化（A6-5 / M-A5-1 / M-A5-2，P1；与 A2-2、A3-7、A4-1 同根因簇 F1/F2）。
5. **编辑器打开期间，任何新命令都会阻塞到用户按 Esc 为止**：`cancelActive()` 的取消能力只覆盖「有活动 prompt」的情况，MTEXT 编辑期间无 prompt，于是 `await promise` 一直等旧的 trigger（A3-3 已确认 P1；A1-2 同簇 F3）。
6. **导出件的中文不可信**：SVG 用独立于画布的逐字符估宽布局，PDF 不嵌入任何字体（实测 jsPDF 4.2.1 只内置标准 14 字体，svg2pdf 对中文统一回落 `times`），导出的「中文」不是中文（A5-6，P1）。
7. **SVG 导出中同名块只出现 1 次且变换连乘**：`AcSvgEntity.fastDeepClone()` 返回 `this`，缓存模板被就地变换（A5-7 已确认 P1，与 `docs/code-review/raw/plugins-heavy.json` 第 1 条为同一缺陷）。
8. **`rotation` 被 `directionVector` 覆盖**：属性面板改 rotation 无任何视觉变化，但 DXF 组 50 仍按新值写出（A2-3 / A4-4，P1/P2，簇 F4）。
9. **`styleName` 未固化**：新建实体样式名为 `''`，渲染随「当前文字样式」漂移；空串经 DXF filer 被写成字符串 `"0"`，即一个不存在的样式名（A1-3 / A2-5 / A5-8，簇 F6）。
10. **空 `contents` 被写成字符 `0`**：`AcDbDxfFiler` 把空字符串值替换为 `'0'`，往返后文字内容被污染（M-A2-1，P2，已实测 `1\n0\n7\n0\n`）。
11. **验证基建已四层落地并可复跑**：B1 字面量层、B2 几何层（真实渲染器 + 离线 `hztxt.shx`）、B3 像素层与端到端层；本次合成实测 `3 suites / 29 tests passed`（见 §5.4）。但像素层**不校验字形身份**，几何层**不覆盖 `width` 自动换行与旋转**，仍有 3 条 `it.failing` 期望失败用例待修复后移除。
12. **对抗式验证显著修正了审计的严重度判断**：40 条 finding 中 confirmed 20、partially-confirmed 19、refuted 1（drop）；13 条下调、1 条上调，并有 18 条审计未报的缺陷被补报（含 2 条 P1），说明「审计 ⇄ 验证」的双向纠错是有效的，不应跳过。

## 5. 绘制结果准确性验证方法（可独立照做）

> 本节自足：读者不看 §6–§8 的缺陷清单，也能按本节把「文字画得对不对」验证起来。

### 5.1 为什么渲染性能优化资料回答不了准确性问题

`docs/02-性能优化/`（瓶颈分析、优化计划、M0–M2 总结、框选性能分析、圆弧 LOD 与渲染数据采集）回答的是**「单位时间画了多少」**，其度量是帧时间、FPS、实体/顶点吞吐、批次数、首帧时延。这些量对「字形是否正确」提供的信息量是**零**，而且是负相关的四个具体理由：

1. **指标不可分辨**。一张 1280×800 画布上 24 px 高的单个汉字墨迹约占 **0.056%** 的像素（B3 与 A5-4 实测：单字 ≈24²=576 墨迹像素 / 1.024e6 总像素）。任何基于「非背景像素占比」「平均亮度」的性能侧统计，都无法区分「字对 / 字错 / 没画字」。
2. **优化手段本身会暂时改变文字外观**。延迟几何（`deferGeometry`）、批处理、`waitUntilIdle` 前的中间态，会让文字在某一帧**故意缺席**；`forExport` 路径又跳过字形延迟（`AcTrView2d.ts:3074-3075`）。用性能指标衡量这些路径，会把「正确的延迟」与「错误的不显示」混为一谈（A6-6、B3 遗留第 3 条）。
3. **性能基线随机器变化，不能作为正确性判据**。而正确性需要的是**与机器无关的不变量**（组码值、行高公式、附着点锚定、墨迹是否落在期望框内）。
4. **优化的自由度与正确性的自由度不在同一维度**。优化可以自由决定「何时画、画多少、合并成几个 batch」；准确性关心的是「画在哪、画成什么形状、画了几个字符、导出是否同源」。

**交叉引用（只在此处）**：唯一与准确性有交集的性能机制是 §9 列出的三条——延迟几何/`forExport` 使导出字形可能不是最终字形、`waitUntilIdle` 只等几何不等字体、批处理包围盒与 `geometricExtents` 是两套口径。清单其余部分请继续遵循 `docs/02-性能优化/`，本报告不重复。

### 5.2 四层验证模型

设计原则：**低层证明「值对不对」，中层证明「布局对不对」，高层证明「画面与链路对不对」，并明确每层的盲区，避免用高层判据替代低层结论。**

#### L1 字面量层（B1）

| 项 | 内容 |
| --- | --- |
| 验证对象 | 命令→实体的落库字段（`location`/`contents`/`width`/`height`/`lineSpacingFactor`/`attachmentPoint`/`styleName`/`layer`），以及 DXF 组码 40/41/50/71 的往返 |
| 判据 | 实体字段必须等于编辑器的**契约返回值**（而不是等于某个硬编码常量）；空/纯空白内容不落库；越界 `attachmentPoint` 回落默认值；`contents` 的内联格式码与首尾空白原样保留；DXF 往返逐字节等价；**组 40 是「每行字高」而非「整块高度」**（2 行时块高 = `2.5 + 5/3×2.5`） |

### 5.3 真值（ground truth）来自哪里

四类真值，按可靠性从高到低：

1. **写入端契约**（最高）：`AcDbMText` 的字段语义 + DXF 组码规范——组 40 = 每行字高、组 41 = 换行参考宽度（0 = 不折行）、组 44 = 相对单倍行距（`5/3 × 字高`）的比值且**默认 1.0**、组 50 = 弧度、组 71 = 附着点 1–9、组 7 = 样式名（空值不得写出）。**注意**：仓库自身在若干处违背了这些契约（组 44 写 0.3、组 7 写 `"0"`、组 41 被改成 1e-4），所以「真值」必须取自规范与 AutoCAD 语义，**不能取自当前实现**——这也是所有回归基准必须人工过一遍的原因。
2. **mtext-renderer 布局不变量**：`LINE_SPACING_SCALE_FACTOR = 5/3`、`calculateAnchorPoint` 的三种锚定语义、`maxWidth = isFinite(width) && width > 0`、`fontSize = height || fixedTextHeight`。这些是几何层的可断言骨架。
3. **CJK 字形度量特征**：`hztxt.shx` 为 BIGFONT 定宽（advance ≈ 1.0236 em，与字符是否为汉字无关）→ 因此 **advance 无法区分 CJK/西文，能区分的是墨迹宽度**；bigfont 的 not-found 字形是全角「？」，非 bigfont 是半角「?」。用「墨迹宽度落在特征区间」作为「字形没退化成空白」的代理判据。
4. **截图墨迹统计**（最低，仅为结构合理性代理）：覆盖率、四边留白、连通域数量、最大连通域填充率、噪点/端点比例、与基线 diff。它**只证明「有结构合理的墨迹」**，不证明「是这个字」。任何用像素统计宣布「文字正确」的结论都必须标注这一限制。

### 5.5 如何在 CI 中落地

**闸门顺序（快 → 慢，失败即停）**

1. **静态闸门**：`pnpm lint` + TypeScript。注意现状：`cad-viewer-example` 的 `npx eslint src/` 目前 **13 errors / exit 1**（含 `AntdRibbonPanel.vue:166` 的动态 key），也就是说这道闸门当前是红的，必须先修或先降级为 warning 才能挂到 CI（见 A1-5）。
2. **L1 + L2（Jest，无浏览器）**：三条 spec + 全包回归 `pnpm test -- packages/cad-simple-viewer packages/data-model packages/three-renderer`。
   - **`it.failing` 计数门禁**：在 CI 中断言「`it.failing` / `it.skip` 的数量等于登记的期望值」，否则「修复了生产代码却忘记去掉 `.failing`」会永远静默、而「悄悄把用例改成 `.failing` 让红转绿」也会无人察觉。这是本套基建最容易失效的单点。
   - **基准文件保护**：对 `mtext-layout-baseline.json` 记 SHA256，基准变更必须在 PR 描述里说明「是实现回归还是基准过时」。
3. **构建**：`pnpm build`（E2E 与像素层都依赖 `packages/*/dist` 为当前包名 `@hy/*`；沿用旧 `dist` 会白屏）。
4. **L4 端到端**：先 `pnpm build`，再 `pnpm --filter @hy/cad-viewer-example test:e2e -- e2e/tests/mtext-draw-accuracy.spec.ts --workers=1`；随后跑 `node bench/verify-text-pixels.cjs` 做区域化像素判据（`--selftest` 每次必跑，用于证明判据本身仍然有效）。
5. **稳定性处理**：
   - **离线字体**：把 `assets/hztxt.shx` 纳入版本库/CI 缓存；把 CDN `baseUrl` 换成本地 `./fonts/` 并**本地化 `fonts.json`**（离线时 `getAvailableFonts()` 抛错会挡住 IndexedDB 回退，A4-3）；E2E 用公开 API 把默认文字样式指向 `hztxt`，避免依赖 `SimKai`（Windows 专有）。
   - **`deviceScaleFactor` 固定为 1**；浏览器统一 `PLAYWRIGHT_BROWSER_CHANNEL=chrome`（或 `playwright install chromium`）。
   - **像素基线只在固定镜像上跑 diff**；其它环境只跑结构判据（覆盖率/留白/连通域），否则换 GPU/驱动/DPR 会全红。
   - 失败时上传 `bench/out/*.png`、`*.region.json` 与判据 JSON 作为产物，便于事后定位「区域给错」还是「真的没画」。
   - Linux 无 GPU 容器下阈值需重标定；`swiftshader` 下的抗锯齿会改变墨迹端点比例。

### 5.6 一页速查（reviewer checklist）

- [ ] 新建文字的字高是否来自**文字样式/`TEXTSIZE`**，而不是屏幕像素折算？换缩放画同一段文字，DXF 组 40 是否一致？
- [ ] `AcEdMTextEditor` 返回的 `height` 与「用户框选高度」「样式字高」三者中，哪一个被写进实体？是否被 `Math.max(1,·)` 之类静默改写？
- [ ] `lineSpacingFactor` 落库值是多少？新建、双击编辑、按 Esc 取消三种路径下 DXF 组 44 是否一致且等于原值（默认 1.0）？
- [ ] 编辑既有 MTEXT 时，**取消**是否产生任何数据库写入（undo 栈是否多出一条）？
- [ ] `styleName` 是否被显式写入？导出的组 7 是合法样式名、空行还是字符 `0`？切当前样式后已画文字字形是否变化？
- [ ] 空内容、纯空白内容、`height<=0`、`width<=0`、越界 `attachmentPoint` 五条边界，分别在哪里被拦、有没有用户反馈？
- [ ] `rotation` 与 `direction` 同时存在时，渲染取哪一个？属性面板改 rotation 有没有视觉变化？`geometricExtents` 与渲染取的是不是同一个真值来源？
- [ ] 缺字体时用户能否看到提示？（worker 模式下 `fontNotFound` 是否被桥回主线程？`missedData.fonts` 是否可能非空？）

## 7. 中文专项

**7.1 字体回退链**（渲染器 `@mlightcad/mtext-renderer@0.12.4`，`dist/index.js`）

```
样式字体 → bigFont(:30054) → 默认字体链 hztxt/simsun (:30068) → symbolFonts (:30073)
        → 任一已加载字体的 not-found 字形 getNotFoundTextShape (:30079)
```
- not-found 字形**要求 `loadedFontMap` 非空**（`:27127-27132`）——字体一个都没加载时，连「？」都画不出，`processChar` 直接走 `processBlank`（`:29922-29923`）。
- SHX bigfont 的 not-found 字形是**全角「？」**（`:26592-26594 fontType===BIGFONT ? '？' : '?'`）；`:30078` 连「有形状但无描边」也会替换成 not-found 字形且**不发事件**。
- 用 `hztxt.shx` 时 CJK 与 ASCII 的 pen advance 相同（BIGFONT 定宽，实测 1.0236 em），所以**回退是否发生只能靠墨迹宽度判断**，不能靠 advance。

**7.2 缺字告警（P1-7 / P1-8）**

| 场景 | 现象 | 覆盖状态 |
| --- | --- | --- |
| worker 模式 + 样式字体缺失（MTEXT/TEXT） | `fontNotFound` 不发、提示不弹、`missedData.fonts` 恒空 | **已确认，链路断开** |
| worker 模式 + 样式字体缺失（SHAPE） | 仍会填充 `missedFonts` 并弹提示 | 与 MTEXT 行为不一致（既存事实） |
| 字体已加载但缺具体字形 | 静默画成「？」/「?」，不计 `missedFonts`、不发事件 | **已确认**；仓库侧从未消费 `getUnsupportedChar`/`unsupportedChars`（全仓仅 `AcTrStyleManager.ts:67` 与 `AcTrMTextRenderer.ts:26` 声明 `unsupportedTextStyles`，无读取） |
| 离线 + 默认 worker 模式 | 汉字整段退化为**空白占位**（有宽度、无字形） | **已确认并实测**（零字体下 6 汉字 → 0 叶子、0 顶点、box `(0,-2.5)-(4.5,0)`） |

影响验证判据：像素层的「覆盖率」判据在离线 worker 模式下会**正确判红**（缺字 <0.1%），但**几何层不会**——它只看 box（占位宽度正常）。这正是必须保留像素层的原因。

**7.3 编码与乱码**

- **空 `contents` 被写成字符 `0`**（P2-19）：`AcDbDxfFiler.ts:581 this._lines.push(text === '' ? '0' : text)`，实测往返后 `contents==='0'`。清空文字后保存，在其它 CAD 中显示一个 `0`。
- **空 `styleName` 被写成 `"0"`**（P3-2）：组 7 = `'0'`，是一个不存在的样式名，其它 CAD 打开后回落到默认样式。
- **换行与转义**：编辑器 `getText()` 走 AST 序列化，换行输出为 `\P`、`\` 与花括号被转义（`mtext-input-box dist/model/ast.js:143-182`），`AcDbMText.encodeMTextContentsForDxf`（`:801-803`）只兜底真实换行——这条路径是**正确的**，`\P` 段落编码经 B1 实测往返无损。
- **DXF 文本编码**：全仓仅支持 UTF-8（pair reader 直接扫描 UTF-8 字节、字符串按需惰性解码，见 CLAUDE.md）。GBK 编码的旧图纸中文会乱码，本批未实测。
- **导出侧乱码**（P1-11）：PDF 中文落到 `times`，内容流为 `(mKÕN-e\u0000A\u0000B\u0000C) Tj`——不是乱码字符而是**字节被当单字节标准字体渲染**，等价于乱码。

**7.4 字高与全角宽度**

- **字高**：`height` 是字高（DXF 40），渲染器 `fontSize = height || fixedTextHeight || 0`。新建路径的字高来自 `24/zoom` 并被夹到 1（P1-1/P2-4/P2-15）；`AcDbMText.ts:815 filer.writeDouble(40, this.height)` 把它永久固化。
- **全角宽度**：CJK 按字体自身 pen advance 前进，**没有 1 em 强算**；`widthFactor` 全局乘到字形与 advance（几何层实测「scales the run with widthFactor」通过）。但三条路径取值不一致：three-renderer 完全不填 `data.widthFactor`（P2-16）、SVG 侧无条件 `× 0.85`（P3-17）、渲染器在窄框时用 `CJK_MTEXT_CHAR_WIDTH_HEIGHT_RATIO = 0.8` 覆盖 DXF 41（P3-16）。
- **「西文窄于汉字」在只有 `hztxt.shx` 时数学上不可判**（BIGFONT 定宽，advance 相同）。B2 把它退化为**墨迹宽度**断言（`i`/`l` 0.260 em 远窄于 `中` 0.685 em），并在注释里写明原因。要真正验证需要 `simplex.shx` 之类的小体积西文 SHX 进 `assets/`。
- **`obliqueAngle`**（P2-11）：中文（SHX bigfont 整体倾斜）与西文同受影响，单位契约矛盾会直接导致「斜体看着没斜/斜错方向」。

**7.5 中文输入（IME）**

`AcApMTextCmd` 的 IME 路径在 A3-6 中被判为「重复上屏」并被对抗式验证**整条 refuted**（见 §8.1）。当前事实：`onImeBeforeInput` 首句 `if (event.isComposing) return` 兜住了两种引擎的提交事件（Chrome：`beforeinput(true) → input(true) → compositionend`；Gecko：`beforeinput(true) → compositionend → input(false)`），插入只由 `compositionend` 执行一次；组件未注册 `input` 监听，不存在二次上屏通道。**不应**按 A3-6 原文加幂等守卫（会破坏 `compositionend` 的清值语义）。残留的是**覆盖缺口**：Jest 为 node 环境且整包 mock，真实组合序列在全仓零覆盖；B3 用 `keyboard.insertText`（等价 IME 提交）绕开了组合事件。建议加一条 Playwright/CDP `Input.imeSetComposition` 用例，断言字符数等于输入字符数。
